# 页面侧性能 P2 残项（推迟中）

> 分类：D · 工程债（性能）｜状态权威：STATUS「性能遗留」条

本文件只承载 2026-02 页面侧性能修订（A1–A6）中**未实现**的 P2 三项（侧栏 T2、factAt 量化、
前置仪表）；已实现部分的契约见 docs/design 的 05 §3（发布门与投影缓存）、14 §8（隐藏期不采样）、
19 §3.2.4（桥探测长尾）、24 F5（purged 孤儿键收敛）。三项都保留证据与设计以便下次决策，
落地前不进入任何提交面。

## 1. 侧栏 T2：更细的上下文拆分与按来源缓存

**证据（代码）**：sidebar 的行状态把 menuOpen/renaming/rowErrors 与全量字段 ctxValue 放在同一条
更新通道上，任何一处的交互都会走到全部 ServerSection 与全部行；搜索通道（client-core 的
search-state.ts）每个按键立即 notify，menus.ts 与 ServerSection.tsx 都订阅它，所以一次键入会
重渲染所有壳的全部行；sessionsOf/orderedWorkspaces/dropEnv 每次渲染按来源重算。

**已知前置（2026-02 落地时记录的实测缺口）**：T1 已给 ctxValue 加 useMemo（全量字段逐项覆盖），
但各 hook 提供的动作回调（toggleMenu/closeMenu/commitSessionDrag/onNewSession 等）目前仍是每次渲染
重建的普通函数，因此 ctxValue 只在回调身份恰好不变时命中；要拿到完整收益需先把这些回调 useCallback 化。

**设计**：menuOpen/renaming/rowErrors 拆成独立 context（只有需要它们的行与 section 订阅）；
sessionsOf/orderedWorkspaces/dropEnv 按 (server 身份, 相关 prefs 字段) 加一层按来源缓存；
搜索通知合并到一次（微任务或帧级），把"每键通知"降为"每帧至多一次"。

**预期收益**：交互提交从 O(全部 section x 全部行) 降到 O(1) 行加 O(1) section；搜索键入从
壳数 x 全行降到一次通知；派生对象数按来源从每次渲染 N 个降到变化时才新建。结构性倍数，不承诺毫秒。

**风险**：context 拆分会让"同一事实两个座位"的同步面变多（menuOpen 与 renaming 当前共用一个
状态源，拆开要保持同一行不会出现半开菜单）；搜索通知合帧后，键入的可见反馈上界从"立即"变成
"下一帧"，需要实机确认主观延迟。现有源码文本锁（session-row-state.test.ts 把 7 个侧栏源文件——6 个 tsx +
server-section-model.ts——读成文本正则断言）在拆分时必须同步更新，否则锁会失真。

**验证**：sidebar 包全部测试 + renderer 接线锁；实机用 Web Inspector 记录"单击 kebab 后的
重渲染行数"与"搜索键入一次的通知次数"前后对比。

## 2. factAt 量化（产品取舍）

**证据（代码 + 实机）**：运行时事实里的 factAt（该行事实的观察时刻，host 域 ms）被刻意纳入
runtimeReportSignature（见 client-core 的 derive.ts 中 runtimeReportSignature 的注释与实现），
于是每次观测都会换签名并触发一次发布；实机风暴锚点为 Dock 徽标 1,098 次翻转 / 40.8 秒
（约 27 次/秒），静息期趋近 0。行的 data-chamber-fact-at 就是这条时间戳。

**设计**：把 factAt 量化到固定桶（例如 1 秒）后再进签名，桶内的观测不再改变签名；原始值仍按
原样进入 runtime facts 供渲染，只在"是否需要重发布"的判据上用量化值。

**预期收益**：风暴期发布频率从"每次观测"降到"每桶至多一次"，是当前已知的最大单一项；
按 27 次/秒的峰值上界，量化到 1 秒最多把发布压到 1 次/秒量级（真实收益取决于观测节奏，需仪表）。

**风险**：这是**产品取舍**而非纯性能修复——行的"事实观察时刻"呈现粒度变粗（数据本身不变），
任何依赖"factAt 一变就重发布"的消费面（新鲜度读数、完成边沿的判定）都要逐一复核；
derive.ts 里那条"刻意纳入"的注释是契约，改动必须同时改写它。发布速率目前无仪表，收益需先加
计数再谈。

**验证**：derive 单测（量化桶边界、桶内等值不发布、桶外仍发布）；实机风暴复测（发布计数与
徽标翻转数）；真机确认行的新鲜度读数仍可接受。

## 3. 搜索通知与 ctx 拆分的前置仪表

**证据**：发布速率、每次发布的订阅者数量、React 提交耗时都没有仪表；风暴 27 次/秒与静息趋零
只是两端锚点，中间的分布（一次交互触发几次发布）不可测。上面两项的收益因此只能给结构性上界。

**设计**：加一个仅开发档可读的计数器（发布次数、每次发布的 servers 变化来源数、签名缓存命中
数、侧栏行派生次数），走既有诊断通道暴露，不新增持久化、不进渲染热路径。

**预期收益**：把 P2 的收益判定从"结构性倍数"升级为实测数字；也是"回收壳蓝点/通知暂停"这类
既有取舍的复核依据。

**风险**：仪表本身不能成为新的热路径成本（计数要无分配、无字符串拼接）；诊断面不得进入打包
产物的用户可见 UI。

**验证**：开发档读一次计数；打包档确认计数器被编译掉或不暴露。
