# 工程实践规范（质量 / 版本 / 交付 / 知识治理）

> **性质：规范**。本文只写"应当怎么做"，不写上游的事实台账（数字、行号、逐条证据不在本文维护）。规则的来源是对上游 dsh `0.1.5-rc.2` 的一次工程治理调研，以及本仓库已有的实践；两者冲突时以本仓库 `docs/design/**` 与 `docs/checklists/**` 的现行契约为准。
>
> **适用对象**：任何改动，无论由人还是 agent 产出。提交前按 §6 自检。

---

## 0. 三条总则

**G1 每条规则都要有执行者。** 一条规则要么挂在门禁、hook、政策脚本上，要么表现为一条明确的"证据要求"。没有执行者的规则会腐化——它会留在文档里，但不再影响行为。

**G2 把"上一阶段的成功"变成可验证证据。** 不要用"我记得它过了"衔接阶段。上一阶段的结论应当是下一阶段能独立核对的产物：一份校验记录、一个完成标记、一次可重放的验证。

**G3 一个事实只有一个家。** 每条知识有唯一归属：规则、决策、现状、动作、失败各归其位；别处只链接。重复表述本身就是缺陷——它保证两处会漂移。

## 1. 质量

### 1.1 门禁分三层，职责不重叠

| 层 | 只负责 | 不负责 |
|---|---|---|
| 提交时（hook） | 快、本地可判定、可自动修复：格式、空白、受保护文件的成对更新、索引态一致性 | 测试、构建、文档全集、覆盖率 |
| 推送前（本地） | **按改动范围选出的最小可失败证据** | 仓库全量矩阵 |
| CI | 穷尽覆盖、平台矩阵、构建产物与集成面 | 替代本地快速反馈 |

> 本仓**不用 hook 承担第一层**（决定与理由见 §7.7）：同一批"窄检查"改由 `pnpm run check:static`
> 显式调用。规则本身保留，但不要把这张表读成本仓已有钩子。

- **R1.1.1** hook 必须窄。任何"顺手多跑一点"的 hook 都会让人绕过它。
- **R1.1.2** 本地不追求与 CI 等价；但"该跑哪些"必须可判定：先算出改动范围，再按"哪个检查会因这次回归而失败"来选。
- **R1.1.3** 不因为"要提交了"而重跑已经通过的检查；不在没有新证据的情况下重复同一命令。
- **R1.1.4** 全量本地预演是**显式开关**，不是默认路径；它也不构成对 agent 的指令。

### 1.2 门禁要有单一入口与命名模式

- **R1.2.1** 仓库级门禁收敛到一个调度入口，本地与 CI 跑**同一集合的不同模式**（如"静态""覆盖率""消费者""文档""发布彩排"），而不是各自维护一张清单。
- **R1.2.2** 调度器必须能校验自己的图：重复 id、未知依赖、依赖成环在任何子进程启动前报错。
- **R1.2.3** 门禁集合本身要有自检：至少有一个检查覆盖"调度器图合法""模式定义完整"。

### 1.3 测试规范

- **R1.3.1 只 mock 昂贵或不确定的边界**（模型、网络、时钟）。下游一律用真实实现。手写的替身只能证明"桥接了字节"，不能证明产品行为。
- **R1.3.2 验证世界，不验证自述。** 断言要重新执行命令或从外部重读文件；对产出物自身输出的关键词探测会让"作弊的实现"通过。未触碰的文件要断言逐字节不变。
- **R1.3.3 测真实入口路径。** 产品可见的能力必须有非单测的真实组合测试；可执行入口要跑**已构建产物**，而不是源码直跑——构建链会掩盖加载、解析、时序与生命周期问题。
- **R1.3.4 只在源码面解析依赖**（测试期），避免加载到第二份模块单例；需要构建产物的测试必须显式声明这一依赖。
- **R1.3.5 测试自带资源生命周期。** 端口、临时路径、子进程由测试自己获取、自己在 teardown 释放，失败/超时/重试路径同样释放。共享夹具放在普通 harness 模块里，绝不被另一个 spec 导入。
- **R1.3.6 一个只有单独运行才通过的测试，是测试的缺陷**，不是环境不稳。按"测试缺陷/真实竞态/外部瞬时"分类处理，不要用抬高超时、加 retry、全局串行化来掩盖。
- **R1.3.7 用户/模型可见的非平凡改动，必须更新一份可重放的端到端基线**（录制回放或等价物）。单测、mock 测试、说明文字都不能替代它。
- **R1.3.8 不改基线来迁就实现**：基线漂移时先判断是产品错了还是基线过时；修基线要单独可见、逐条审阅。

### 1.4 覆盖率规范

- **R1.4.1** 覆盖率是**合并门禁**，且逐文件计算——一个覆盖良好的大文件不能补贴一个裸文件。
- **R1.4.2 未覆盖的行首先是"待删代码"的信号**，而不是"待补测试"的工单。加测试前先问这行为什么存在。
- **R1.4.3** 行覆盖必要而不充分：它证明行跑过，不证明功能按发布形态可用。
- **R1.4.4** 豁免要是有门槛的机器对象（名单 + 准入规则 + 守卫测试），并逐处给出理由；"临时忽略"必须带原因字符串。

### 1.5 不变量与反向证明

- **R1.5.1** 任何不变量都要挂到一个实际执行的门禁上。
- **R1.5.2 新护栏必须附反向证明**：引入回归 → 观察它变红 → 回退。没有失败样例的护栏只是装饰。
- **R1.5.3** 决定要在"做出该决定的那一步"强制，而不是在旁路：schema 省略、包装层、调用顺序、文档约定都不算强制。拒绝路径要从执行器测出来。
- **R1.5.4** 例外必须窄且具名；禁止用全局关闭规则来换绿。

### 1.6 反假绿

- **R1.6.1** "没跑"不等于"通过"：聚合结果里 **skipped 与 failed 同等对待**。
- **R1.6.2** 缺少凭据/环境导致的跳过，必须在应当阻断的场合**硬失败**（宁可红，不要静默绿）。
- **R1.6.3** 对"自跳过"要专门设防：断言实际执行数量，而不是只看退出码。
- **R1.6.4** 门禁必须防止**空语料**：空集合不能算通过。

### 1.7 文档与代码的等价

- **R1.7.1** 文档里粘贴的接口/类型，必须能**回源比对**（机器抽取源码声明与文档逐字核对），并有 1:1 的清单；粘贴块与源码漂移即失败。
- **R1.7.2** 文档中可编译的代码块必须真的编译。
- **R1.7.3** 交叉引用必须机器可校验（相对链接 + 锚点存在），禁止裸文件名与编号。
- **R1.7.4** 常设文档设字数上限；触顶流程固定为"**搬家 → 压缩 → 抬顶**"，抬顶必须在 PR 里论证。

### 1.8 设计期质量（前置规则）

- **R1.8.1 每个抽象都要有当前的主人与需求**：绑不到当前契约或生产消费者的抽象、开关、兼容路径、防御性拷贝，一律不加。
- **R1.8.2 公开选择要有证据**："可配置"不能证明某个默认值、公开操作集或格式合理；没有消费者证据就要求显式取值或推迟。
- **R1.8.3 派生状态只在提交点发布**：操作成功后才发通知、才更新派生缓存。
- **R1.8.4 边界加在完整结果上**：字节/token/条目/时间上限要覆盖含包装与元数据的整体，并测极小值、精确边界、超大单块与多字节边界。
- **R1.8.5 越界失败要响**：自包含的配置错误在加载期失败，其余在最早可判定处失败；绝不静默跳过缺失的引用对象。

## 2. 版本

- **R2.1 版本只有一个来源，而且落在仓库里。** 版本写在清单与锁文件里、由人提交、由人打 tag；CI 只读不写。禁止在 CI 里推导版本号。
- **R2.2 同一发布单元共享一个版本线。** 属于同一发布单元的包版本必须一致，并由常驻门禁维持（而不是靠发布时记得检查）；跨包引用一律使用工作区协议，不手写范围。
- **R2.3 预发布用版本串表达，通道由版本决定。** 不靠分支推导通道；预发布与正式版走不同的分发标签，且预发布同样构成"已发布"义务。
- **R2.4 API 可以激进，持久化必须保守。** 未稳定的公开 API 可以整体改并同步所有消费者；但**已发布的数据格式永不改写已提交的世代**，只允许新增带版本名的后继，并且旧世代不隐含回退或降级支持。
- **R2.5 标记语义绑定发布。** 用统一的注释标记区分"应阻塞发布""应尽快修""某天再说"三档，让任何扫代码的人能分清发布阻塞与随便。
- **R2.6 变更单元要自带证据。** PR 必须写清：动机（引用同仓库 Issue）、改了哪些命令/配置/API/协议/持久化与哪些可观察行为、以及**每种验证方法一个条目 + 可复核证据**。禁止只凭类型或静态检查声称运行时行为正确。
- **R2.7 历史要可读。** 独立变更拆开；修问题先修引入它的那个变更；重写历史只用"带租约的强推"并明确禁止裸强推；已评审的修复不要从历史里 amend 掉。
- **R2.8 决策记录随事实更新，但不承载计划。** 已落地的决策记录同步路径/名字/结构；计划式、验收清单式的措辞一旦落地就该被改写掉。

## 3. 交付

- **R3.1 打包与发布分离，凭据只出现在发布侧。** 彩排（打包 + 依赖布局 + 安装验证）在每次 PR/主干推送都跑，且**不带任何凭据**；真正的发布是显式人工触发的独立流程，且**不出现在 PR 检查面板里**。
- **R3.2 发布身份由流程自己复核**，不靠操作者记得：必须从 tag 触发、tag 属于本发布家族、tag 指名的版本正是本次要发的版本、发布顺序在构建前就已解析完成。
- **R3.3 发布必须幂等可重跑。** 逐个产物对目标仓库判定：不存在 → 发布；已存在且内容摘要一致 → 跳过；已存在但摘要不同 → **失败**（含义是"内容变了却没升版本"）。对瞬时失败做有界重试并每次重新判定，不盲重试。
- **R3.4 发布顺序是一等产物。** 顺序由依赖关系推导并落盘；它同时是中断恢复的地图——一次中断的发布只会留下顺序的一个前缀，所以顺序必须在每个 PR 上可审查。
- **R3.5 验证"装出来的东西"。** 用发布产物在仓库**之外**的一次性环境里安装并驱动可执行入口，环境要清洗（剔除会隐式改变行为的变量、pin 掉 HOME 类路径）；工作区链接与残留构建产物不能在这里冒充成功。
- **R3.6 观测型先于阻断型。** 不稳定的检查先以观测身份进 CI 面板收集信号，稳定后再转为阻断；阻断集合必须显式列名，且"必需判定"只认一个稳定的聚合结论。
- **R3.7 授权与政策即代码。** 审批门槛、PR 元数据规则、发布开关都写成可单测的脚本；执行政策的作业必须从**受信分支**取政策、把待审数据只当数据；发布授权应优先使用可审计的仓库变量/OIDC，而不是长期凭据。
- **R3.8 通道越少越好，且"没有的通道"要写明。** 每多一个分发通道就多一套签名、更新、回滚与文档义务；默认不新增通道，删除通道也要留决策记录。
- **R3.9 产物不可变、元数据最后写。** 先上传不可变的版本化产物，最后才更新"最新版本"指针且不可缓存；历史产物只增不删。

## 4. 知识治理

### 4.1 知识分层（六层各管一件事）

| 层 | 管什么 | 不写什么 |
|---|---|---|
| 常设指令 | 每次工作都要在上下文里的规则，一条几行 + 指向它的 home | 故事、示例、情境化流程 |
| 决策记录 | 为什么这么定、放弃了什么、需要什么验证 | 计划、验收清单、迁移步骤（落地后） |
| 现状文档 | 现在是什么 | 变更史、PR 号、"以前/现在" |
| 可执行动作（技能/清单） | 怎么做（步骤化） | 设计理由 |
| 失败记录 | 为什么没拦住、新增了什么护栏 | 设计决策 |
| 生成物 | 从源码再生成的目录/清单 | 手工编辑 |

- **R4.1.1** 每类事实只有一个家，别处只链接；发现同一规则出现在两处，就地合并。
- **R4.1.2** 子树可以有更具体的指令文件，但只补本子树规则，不重复全局规则。

### 4.2 决策记录规范

- **R4.2.1 非平凡变更必须带一份决策记录**，且与代码同一个变更单元；只有纯机械/局部改动豁免。
- **R4.2.2 记录必须包含被否的替代方案**，每个给一句"为什么没选它"。没有这一节的决策记录会招致反复争论。
- **R4.2.3 状态与内容一致**：提案态的写法（将来时、验收条件）在落地后要改写成现在时的事实描述；门禁应当拒绝落地的记录里残留计划语气。
- **R4.2.4 新记录触发取代检查**：搜索覆盖同一机制的旧记录，并把被取代的、符合条件的旧记录在同一个变更里退役。
- **R4.2.5 退役是封存而非删除**（有价值的）：封存后不可编辑，也不再作为当前行为的权威；索引由约定或检索承担，不建中心索引。
- **R4.2.6** 记录里引用代码/文档用相对链接，保证可校验、可随移动修复。

### 4.3 现状文档规范

- **R4.3.1 只写当前状态。** 禁止叙述历史（"以前/现在/不再/重命名过"）、禁止 PR/提交号、禁止实现状态标注（"已实现""将来"）——状态会腐烂，权威在代码与清单。
- **R4.3.2 分教程与参考两类**，不要把"循序渐进的教学"和"可查阅的契约"混在一篇里。
- **R4.3.3 不手抄目录/接口/清单**：源码或生成器是权威，文档只链接。
- **R4.3.4 一段一行**（用编辑器软换行），便于 diff 与评审。
- **R4.3.5 术语唯一**：一个概念一个规范词；避免把"门禁""面""词汇"这类比喻当作精确术语。
- **R4.3.6 写作反模式清单**（评审时逐条对照）：同规则多处表述 · 历史叙述 · 状态标注 · 手抄目录 · 推理过程记录 · 理由散落在兄弟方法旁 · 段落墙 · 强调通胀。

### 4.4 双语文档规范

- **R4.4.1 三种文件成对出现**：原文、译文、一致性记录；一个变更不得只落一侧。
- **R4.4.2 一致性用内容哈希记录**（不是提交号），因此同一变更内的编辑也能被判定；重新记录是一个**可评审的动作**，不是一次自动盖章。
- **R4.4.3 结构必须一一对应**：标题层级与顺序、列表种类与条目数、表格行列、代码块、链接目标（含锚点）。
- **R4.4.4 合并要 fail-closed**：冲突无法安全推导时留下普通冲突并给出恢复路径，绝不产生"看起来干净但未验证"的结果。
- **R4.4.5 写下门禁的极限**：绿灯只表示"这些内容在某次确认时是一致过的"，不表示确认本身可靠；敷衍的重录能过门禁，但不应过评审。

### 4.5 每份契约都有归属

- **R4.5.1** 每个可独立使用的单元（包/插件/服务）都要有一份**契约 README**：配置、语义、限制、扩展点，以及对模型可见效果（模型看到什么、token 影响、缓存影响）。
- **R4.5.2** 契约文档的结构应被门禁钉住（章节齐备、摘要长度、限制章节存在或进白名单），否则它会随作者心情漂移。
- **R4.5.3** 行为变更与契约文档、接口注释同一个变更；不允许"先合代码，文档随后补"。

### 4.6 流程要可被直接调用

- **R4.6.1** 把固定流程（推送前自检、评审、发布、上游同步、故障诊断）写成**可被直接调用的动作文件**，其说明字段写"**什么时候该用我**"，而不是内容摘要。
- **R4.6.2** 动作文件引用规则时用链接，不复制规则文本。

## 5. 反模式清单

**写代码时**
- 为一个静态类型已经保证的值再加运行时校验与"恶意输入"测试（该在解析/配置/持久化/进程/线路边界做）。
- 用包装层、schema 省略或文档约定"实现"一条策略，而执行路径可以绕过它。
- 加一个没有当前消费者的开关/兼容分支，理由是"以后可能有用"。
- 把上限加在内部片段上，而完整的输出（含包装与元数据）仍然无界。

**写测试时**
- 用 mock 掉被验证对象本身，得到"桥接正确"的假象。
- 让断言检查被测对象自己的输出文本。
- 只在源码模式跑入口，从不碰构建产物。
- 让测试依赖固定 sleep；或者让资源只在自己机器上被释放。
- 覆盖率红了就补一行调用，而不是问这行为什么存在。

**做发布时**
- 让 CI 写版本号或提交。
- 把发布做成"PR 里点一下"，或让发布作业出现在 PR 检查面板。
- 阶段之间靠人记忆衔接（"上一步应该过了"）。
- 打包阶段就注入发布凭据；或重试时不做重新判定。
- 静默跳过缺失的凭据/环境，把红变成绿。

**写文档时**
- 在文档里叙述历史或标注实现状态。
- 同一规则写在两处。
- 手抄一份会变的清单。
- 只更新一侧的双语文档，并把"重录一致性"当成完成。

## 6. 自检清单

**提交前**
- [ ] 我的改动属于哪一类（行为 / 契约 / 流程 / 文档）；对应证据跑了哪一条，命令与结果是什么。
- [ ] 新增的行为有没有对应测试，且该测试在回归时会失败（必要时做一次反向验证）。
- [ ] 新增/变更的不变量是否挂到了实际执行的门禁上。
- [ ] 决策记录是否与代码同一变更；是否记录了被否的替代方案。
- [ ] 双语文档是否同步；生成的清单/目录是否重新生成。
- [ ] 没有靠"重跑一遍已经通过的东西"来充当验证。

**新增门禁时**
- [ ] 它作用于空集合时会发生什么（必须失败而不是通过）。
- [ ] 它自己有没有测试，覆盖"接受"与"拒绝"两侧。
- [ ] 它是阻断的还是观测的；如果是观测的，退出条件是什么。
- [ ] 它的失败信息是否足以让人不再需要读源码。

**发布前**
- [ ] 发布身份（tag/版本/家族）是否由流程自行复核。
- [ ] 彩排是否无凭据、且与发布使用同一份产物。
- [ ] 是否验证了"装出来的东西"而不只是"打包成功"。
- [ ] 发布记录（版本线 + 证据）是否已推进，且不超前于仓库。

**改动文档时**
- [ ] 这条事实的家在哪里；我是不是在第二个家重复它。
- [ ] 是否只在写当前状态；是否把历史留给了决策记录或提交。
- [ ] 引用的链接与锚点是否仍然有效。

## 7. 边界：这些规则要打折或不适用的地方

1. **覆盖率 100% 不是普适目标。** 对 GUI、平台相关、依赖真实外部环境的代码，逐文件满覆盖的成本远高于收益。这些面应当用"可重放基线 + 真实机验收"覆盖，并把豁免显式化、写明理由。
2. **记录制度的规模要与团队匹配。** 大量决策记录 + 封存账本的收益来自"人多、决策被反复重提"；小团队照搬规模会先得到仪式感，后得到负担。可先只借"非平凡变更必须带一份记录"和"必须写被否方案"两条。
3. **门禁覆盖本身需要定期审计。** 规则写在文档里、执行者在别处，二者会漂移。应当定期做一次"规则 ↔ 执行者"对照，并把**只能靠评审**的部分显式标注出来——不要假装它已被强制。
4. **机器强制与评审的边界要写清。** 哪些是门禁、哪些是评审责任，必须写在规则旁边；否则读者会把"有门禁"误读成"已保证"。
5. **不要按"门禁数量"对标。** 有效的治理来自"规则有执行者"与"失败会变成新护栏"这两件事；门禁数量多但没人调用（或空转）不构成强度。
6. **不要照抄别人的取舍。** 供应链固定策略、通道形态、是否使用长期凭据、是否发布到公共仓库，都是与发布环境绑定的决定；借鉴结论前先确认自己的约束是否相同。
7. **本仓不装 git hook（2026-12 决定，见 `docs/progress/STATUS.md` 范围决策）。** 理由：`core.hooksPath` 不随 clone 携带，钩子等于要求每个 clone、每台机器各配置一次；而它要跑的窄检查都已是普通门禁，`pnpm run check:static` 一条命令即可。§1.1 的"提交时"层在本仓因此**无人执行**——这是**有意的**，不是遗漏：不要把 §1.1 读成本仓已强制。
8. **R4.3.4（一段一行/软换行）在本仓只对 `packages/*/README.md` 成立；`docs/**` 一律硬换行**（实测平均行长 35–55 字符，终端与 diff 可读性优先）。写新文档时跟随所在目录的既有形态，不要为符合本条去重排既有文档。
9. **双语一致性门只覆盖 `docs/` 顶层的 5 对**（README / DEVELOPMENT / CONTRIBUTING / CHANGELOG / THIRD_PARTY_NOTICES，记录在 `docs/i18n-record.json`，门 = `pnpm run verify:i18n`）。`packages/*/README.i18n.yaml` 三元组是 fork 惯例，当前**没有门禁校验**——那里的绿灯不存在，别把它读成"已一致"。`AGENTS.md` 是英文单语（用户决定），`docs/design|checklists|progress` 与 chamber 自有包 README 是中文单语。
10. **包 README 的模块清单是包级导览，不是权威目录**（R4.3.3 对本仓的打折）：仓内惯例（`packages/desktop/README.md` 同形），权威仍是源码、`package.json` 导出与生成物。
11. **本仓没有"每变更一份决策记录"的载体（R4.2.1 / R4.2.4 / R4.2.5 不适用）**：chamber 的知识分层是 `docs/design/**`（契约，契约类改动含"被否方案"节）+ `docs/progress/STATUS.md`（开放项与取舍）+ `CHANGELOG.md`（发布差异）+ git 历史，没有可封存、可检索的 note 语料。R4.2.2 以"设计文档里的被否方案"落地且**只对契约类改动**强制、靠评审；R4.2.3 的"计划语气"同样没有门禁——**不要把绿灯读成这两条已满足**。
12. **R3.2 在本仓不是"只允许 tag 触发"，而是"两种入口都必须自证身份"**：tag 推送与 `workflow_dispatch`（带必填 version 输入）都是受支持入口，但二者都必须过 `release.yml` 的 `Bind release tag to the checked-out commit`——断言 checkout SHA == 工作流 SHA、`v<version>` 家族与 version 一致、tag 若已存在必须 peel 到本次 SHA，且该步骤被 `pnpm run test:release-workflow` 钉住。读到 R3.2 时按这条形态理解，不要据此认为手动 dispatch 违规。
